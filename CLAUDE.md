# Second Brain — LLM Wiki

A Karpathy-style LLM Wiki for professional knowledge. The LLM synthesizes raw source material into durable, interlinked wiki pages that compound over time.

## Architecture

- **`raw/`** — Source material. Immutable once ingested (row in `wiki/log.md`).
- **`wiki/`** — LLM-maintained wiki pages. Single flat directory.
- **`wiki/index.md`** — Table of contents, maintained by the LLM.
- **`wiki/log.md`** — Ingest log tracking what was processed (newest entries first; existing rows are never edited).
- **`reports/`** — Derived, point-in-time compilations generated from the wiki (e.g. talk prep, summaries). Flow: `raw/` → `wiki/` → `reports/`.
- **`meetings/`** — Meeting protocols generated by `/ingest` from Teams transcripts, plus `glossary.md`. Not part of the wiki.
- **`projects/`** — Time-bound work with a start and an end. One subfolder per project; done when all acceptance criteria are met.

## projects/ conventions

- **Structure**: one subfolder per project, `projects/<project-slug>/`. Each contains a mandatory `project.md` plus any working files (drafts, prototypes, slides, test data).
- **Frontmatter of `project.md`**:
  ```yaml
  ---
  type: project
  title: "Project Title"
  status: active        # active | paused | done | cancelled
  started: 2026-10-27
  ended:                # set when status becomes done or cancelled
  owner: Your Name
  related_wiki: []      # wiki pages the project uses or feeds (without .md)
  ---
  ```
- **Required sections in `project.md`**: Goal (1–3 sentences), Acceptance criteria (`- [ ]` checklist of verifiable criteria — the only definition of "done"), Current state / next step, Log (dated entries, newest first).
- **Lifecycle**: `active ⇄ paused`; `active → done` once every acceptance criterion is checked; `active/paused → cancelled` with a reason in the log. Only the user sets `done` or `cancelled` — the LLM may propose it.
- **Changing acceptance criteria** is allowed but must be recorded with date and reason in the log.
- **Language**: German or English, whatever fits the project or audience.
- **Not part of the wiki** — projects are never ingested and not listed in `index.md` or `log.md`.
- **Closing a project**: write a closing note into `raw/` (outcome, learnings, decisions) and run `/ingest`, so durable knowledge reaches the wiki only via `raw/`.
- Finished projects stay in place; `status` marks them as closed (no archive folder).

## meetings/ conventions

- **One file per meeting**: `meetings/YYYY-MM-DD-<slug>.md`, flat, slug = lowercase hyphenated meeting title. Generated by `/ingest` from a transcript in `raw/`, status always starts as `draft`. Rules: `.claude/commands/ingest.md`, section "Transcripts".
- **Frontmatter**: `type: meeting`, `title`, `date`, `participants`, `source` (link to the `raw/` transcript), `topics` (wiki pages touched), `ingest` (`false` = confidential: protocol only, no wiki changes), `status`.
- **Sections**: decisions, not decided, tasks (owner, due as ISO date, status, timestamp), open questions. Participants' names appear only in the protocol.
- **Glossary**: `meetings/glossary.md` — speech-recognition corrections (names, products, acronyms), read before every transcript. Lives here because it contains names.
- **Not part of the wiki** — protocols are not listed in `index.md` and are never ingested. Wiki knowledge reaches `wiki/` only through the approved topic-page changes of `/ingest` on the transcript. Topic pages may link to a protocol as origin (`Meeting [[YYYY-MM-DD-<slug>]]`), but contain no names or roles.
- **Language** follows the meeting; frontmatter keys stay English.

## reports/ conventions

- **Naming**: `YYYY-MM-DD-<topic>.md`, flat structure.
- **Frontmatter**: `type: report`, `title`, `date`, `purpose`, `based_on` (list of wiki pages used, without `.md`).
- **Snapshots** — reports are not maintained and not listed in `index.md` or `log.md`.
- **Never ingested** — they derive from the wiki, so ingesting them would be circular.
- **Language** follows the audience (wiki content follows the source language).
- New insights that emerge from a report are captured as a separate note in `raw/` and go through `/ingest`.

## raw/ conventions

- **Flat structure** — all files live directly in `raw/`. No subdirectories required.
- **No naming convention enforced** — any descriptive filename works. Low friction intake is more important than consistent naming.
- Files are **immutable once ingested** — never edit or delete a file after its row is in `wiki/log.md`. Enforced by a PreToolUse hook (`scripts/protect_raw.py`, configured in `.claude/settings.json`) for file tools and common shell writes.
- **Before that**, only LLM-authored notes (from conversations, project closing notes, grilling sessions) may be amended: corrections the user gives during the ingest proposal go straight into the note, not into a new one. External sources (transcripts, articles, mails, PDFs) always stay verbatim; a user correction to them goes into a separate short note.
- Supported formats: Markdown, meeting notes, PDF transcriptions, article captures, Teams transcripts as `.vtt` or `.docx` (converted to Markdown by `/ingest`; the original stays).
- **Meeting transcripts**: named `YYYY-MM-DD-meeting-<slug>.md`. The LLM prepends a frontmatter (`type: transcript`, `date`, `participants`, `speakers`, `context`, `completeness`, `language`, `source_original`); the transcript text itself stays verbatim. `source_original` marks the Teams original as converted.

## wiki/ conventions

- **Flat structure** — all pages live directly in `wiki/`.
- The LLM decides page granularity (when to create new pages vs. extend existing ones).
- Language: **follows the source**. Wiki content uses the language of its sources (e.g. a German source yields German pages), and terms stay as written in the source. Existing pages are not translated.
- Links between pages use `[[page-name]]` format (without `.md` extension).
- Every wiki page (except `index.md` and `log.md`) must have YAML frontmatter.

## Page layout

The wiki is read primarily by agents (Claude, coding harnesses), secondarily by humans. Pages from reference sources (books, articles, docs, notes) use one fixed layout so an agent finds the same kind of information in the same place:

1. **Summary** — 2–4 sentences: what the concept is and why it matters.
2. **Core content** — fixed sub-sections with lists and tables rather than prose; pages of the same kind use the same headings (e.g. patterns: when to use, risks, playbook, example flow).
3. **Apply** — concrete rules or a checklist in the imperative, directly usable by an agent.
4. **Caveats** — the source's own limitations, uncertain or estimated values, and anything that is the LLM's interpretation rather than the source's statement.
5. **Source** — where in the source the content comes from (chapter/section numbers, file).
6. **Related** — `[[wikilinks]]` to neighbouring pages.

Principles: one page per concept (an agent loads only what it needs); terms exactly as in the source and its glossary; no decoration (anecdotes, marketing tone); figure content is transcribed into text, images are not copied. Hub pages may add an overview or map instead of Apply. Meeting knowledge follows the transcript rules in `.claude/commands/ingest.md`.

## Frontmatter schema

```yaml
---
title: "Page Title"
sources:
  - raw/2026-10-23-source-file.md
created: 2026-10-23
updated: 2026-10-23
tags: [kubernetes, networking]
related: [service-mesh, load-balancing]
status: draft        # draft | reviewed | outdated
confidence: high     # high | medium | low
---
```

| Field | Description |
|-------|-------------|
| `title` | Human-readable page title |
| `sources` | List of raw/ files this page synthesizes (for meeting knowledge also the protocol in `meetings/`) |
| `created` | Date the page was first created |
| `updated` | Date of the last substantive edit |
| `tags` | Topical tags for discoverability |
| `related` | Other wiki pages (without `.md`) that are conceptually linked |
| `status` | `draft` = first pass, `reviewed` = user-verified, `outdated` = needs refresh (see Status lifecycle below) |
| `confidence` | `high` = well-sourced, `medium` = reasonable synthesis, `low` = speculative or thin sourcing |

## Status lifecycle

```
draft ──(user verifies)──→ reviewed
  ↑                            │
  │                      (new material /
  │                       age > 6 months)
  │                            ↓
  └──(page updated)─────── outdated
```

- New pages always start as `draft`.
- Only the user decides `reviewed` — the LLM never promotes a page on its own. On the user's explicit instruction the LLM sets the field, also in bulk (e.g. "all pages from source X except Y"); the batch is named in the commit message.
- `reviewed` means: the page is a faithful synthesis of its sources (and correct where the user has own knowledge). It does not mean the user agrees with a source's opinions.
- Large ingests are reviewed by sampling: the LLM proposes 2–3 representative pages per block plus every page with `confidence: medium` or `low`; if those pass, the user releases the whole block.
- `outdated` is set automatically by `/ingest` when new raw material updates a `reviewed` page, or set manually when a page's sources are older than 6 months.
- When an `outdated` page is updated, it returns to `draft` — the new content is unverified.

## Ingest behavior

Ingestion is **semi-automatic**:
1. The LLM scans `raw/` for files not yet recorded in `wiki/log.md`.
2. For each new file, the LLM proposes changes (new wiki pages or updates to existing ones).
3. The LLM **waits for user confirmation** before writing any wiki changes.
4. After confirmation: writes/updates wiki pages, updates `index.md`, prepends new rows to `log.md` (below the table header).

## Skills

- `/ingest` — Process new raw files into wiki pages; meeting transcripts also get a protocol in `meetings/` (one approval per transcript).
- `/query` — Ask questions against the wiki, get answers with citations.
- `/lint` — Check wiki health (broken links, missing index entries, stale pages).
- `/review` — Review `draft` pages by sampling and set `reviewed` on the blocks the user releases.
